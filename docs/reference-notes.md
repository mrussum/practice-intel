# Reference notes

Working notes for the reference build: a short plan at the start of each phase,
assumptions made along the way, and a closing review. `docs/DECISIONS.md` is
the owner's log and is deliberately left untouched.

## Global assumptions

- **Model IDs** come from env (`ANSWER_MODEL`, `FAST_MODEL`). Defaults are
  `claude-sonnet-5` (answers, fit analysis) and `claude-haiku-4-5`
  (extraction, routing, summarising, eval judge). I checked both against the
  current Claude API model table (cached 2026-06), not from memory.
- **Embeddings**: `voyage-3-large` (1024 dims) by default, or OpenAI
  `text-embedding-3-small` with `dimensions: 1024`. Voyage's docs site was
  blocked from the build sandbox, so I confirmed the names from the published
  `voyageai` and `openai` npm packages. The `voyageai` package also names a
  `voyage-4` family. Check the Voyage docs before switching; it's one env var.
  Both providers go through `fetch` (no SDKs), which keeps dependencies down.
- **Fakes by default**: `FAKE_AI=1`, or a missing `ANTHROPIC_API_KEY`, selects
  deterministic fakes for the LLM. A missing embedding key does the same for
  embeddings. The app says it's in demo mode (`/ready` and a UI badge) rather
  than silently pretending.
- **Storage**: Postgres + pgvector through a `Store` interface. An in-memory
  store implements the same interface. It's used by route tests and by evals
  in CI, and at runtime only when `DATABASE_URL` is unset (logged as a
  warning). The Postgres store has its own integration test (testcontainers).
- **zod upgraded 3 → 4** (zod is on the approved list): v4 ships
  `z.toJSONSchema`, which feeds Claude structured outputs straight from the
  shared Zod schemas, so each schema is written once.
- **One resume at a time**: uploading a new resume replaces the old one.
  Jobs get the next free number after the current highest ("Job #3"). If the
  highest-numbered job is deleted, its number can be reused. A persistent
  counter would stop that, but it isn't worth another table for a
  single-user tool.

## Phase 1 — Data + ingestion (plan)

**Files**
- `packages/shared`: add `ResumeProfile`, `DocumentDetail`, `ReadyResponse`,
  `ApiError`. Add `ref` to `Citation` (see Phase 2).
- `apps/api/src/config.ts`: AI/embedding/model/limit env vars.
- `apps/api/src/db/schema.ts`: Drizzle tables `documents`, `chunks`
  (`vector(1024)` + generated `tsvector` with GIN, HNSW cosine index),
  `sessions`, `messages`, `fit_cache`.
- `apps/api/drizzle/*.sql`: generated by `drizzle-kit generate`.
  `src/db/migrate.ts` creates the `vector` extension, then runs the migrator
  (`pnpm db:migrate`).
- `src/store/types.ts`, `src/store/memory.ts`, `src/store/postgres.ts`.
- `src/lib/parse.ts`: PDF (unpdf), DOCX (mammoth), TXT/MD. Checks the
  extension, the declared MIME type and magic bytes.
- `src/lib/llm.ts`: `LLM` interface (`structured`, `stream`) with Anthropic
  and fake implementations. `src/lib/embeddings.ts`: `Embedder` with Voyage,
  OpenAI and fake (feature-hashed bag of words, so fake retrieval is still
  lexically meaningful).
- `src/lib/extract.ts`: JobProfile / ResumeProfile extraction. Structured
  output, then Zod validation, then one repair retry that feeds the validation
  error back, then a clear 422.
- `src/services/ingest.ts`: parse → chunk → batch embed → extract → store in
  one transaction.
- `src/routes/documents.ts`: `POST /documents` (multipart, 5MB, one file,
  `kind` field), `GET /documents`, `GET /documents/:id`,
  `DELETE /documents/:id`. `src/routes/health.ts`: `/ready` pings the store.

**Tests**: parser fixtures (txt/md/docx/pdf built in-test), extraction
retry/failure, fake embedder properties, ingest route via `app.inject()` with
the memory store and fakes, and a Postgres store integration test via
testcontainers (skipped when Docker is unavailable).

**Assumptions**
- Ingestion is synchronous inside the request. Documents are small (≤5MB,
  typically 1–3 pages), so a queue would add moving parts for no user benefit
  locally. The README covers the SQS path for production.
- Test fixtures for DOCX/PDF are generated inside the test (a DOCX is a zip,
  and I hand-assemble a minimal PDF). This avoids committing binaries and
  adding a zip/PDF writer dependency.
